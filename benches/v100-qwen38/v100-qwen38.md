# V100 + RTX 3060 Ti fork benchmarks

These benchmarks are for the Qwen3.8 long-context fork. They are not generic llama.cpp performance claims.

## Hardware and build

- Tesla V100 SXM2 32 GB
- GeForce RTX 3060 Ti 8 GB
- CUDA build for `sm70;sm86`
- Fresh benchmark power limits: RTX 3060 Ti 200 W, V100 300 W
- Fork benchmark commit: `b403a781e`
- Previous controlled upstream base: `0e1d9185c`
- Fresh vanilla master check: `bb4caa754` (`0.2.0-dev`)

The benchmark scripts accept environment-variable overrides for model paths, binaries, result directories, GPU UUIDs, and ports. The defaults match the development machine used for the measurements below.

## Main workload

The controlled long-agent workload is:

1. restore an exact real 100,000-token semantic KV/recurrent state;
2. process the identical next 1,000 prompt tokens;
3. generate 64 tokens with seed 1234;
4. compare prompt processing (PP), token generation (TG), generated tokens, and MTP acceptance.

The saved sequence and state used during development were:

```text
results/cache100k-sharedstate-ab/seq.json
results/cache100k-sharedstate-ab/slots/cache100k.bin
```

Given the 101k-or-longer token-ID sequence, rebuild the exact real 100k slot with:

```bash
./benches/v100-qwen38/qwen38-prepare-cache.sh
```

The preparation script processes exactly the first 100,000 token IDs with the same Qwen3.8 dual-GPU/MTP geometry and saves `cache100k.bin`. The benchmark script then asserts `n_restored == 100000`, `cache_n == 100000`, and `prompt_n == 1000`, so a stale or incompatible slot cannot silently turn into a different workload.

Run the dual-GPU A/B with:

```bash
./benches/v100-qwen38/qwen38-100k-ab.sh
```

The fork side adds:

```text
--prefill-reuse 1024
--pipeline-copies 2
--spec-draft-ubatch 1024
```

Both sides use the same model, `--tensor-split 64,2`, q8_0 target KV, F16 draft KV, MTP `n=2`, and the same saved 100k state.

Run the V100-only A/B with:

```bash
./benches/v100-qwen38/qwen38-v100-only-ab.sh
```

The V100-only placement uses `--gpu-layers 63 --ubatch-size 1024`. Layer 64 did not leave enough transient MTP workspace.

## Latest vanilla-master check

On 2026-08-21 the upstream worktree was updated from `0e1d9185c` to current `master` `bb4caa754`. The 20 intervening upstream commits did not overlap any file changed by this fork.

Exact 100k + 1k + 64 dual-GPU result:

| implementation | PP tok/s | TG tok/s | MTP accepted | output |
|---|---:|---:|---:|---|
| vanilla master `bb4caa754` | 313.98 | 26.17 | 37 / 52 | reference |
| fork `b403a781e` | **447.11** | **26.20** | 37 / 52 | identical |

The fork is **+42.40% PP** versus current vanilla master in this run. TG differs by only +0.12%. The generated 64-token sequence and content are identical.

## GLM-5.2 orientation benchmark

A real 100k GLM-5.2 semantic prime is much slower, so GLM was measured separately at 10,000 cached + 1,000 new + 64 generated. These rows must not be compared directly with the 100k table. RTX 3060 Ti-only was intentionally not tested.

| Hardware | MTP | Fork PP | Upstream PP | Fork TG | Upstream TG |
|---|---|---:|---:|---:|---:|
| V100 + 3060 Ti | off | 46.00 | 46.03 | 4.47 | 4.40 |
| V100 + 3060 Ti | on | 44.44 | 44.68 | 6.29 | 6.26 |
| V100 only | off | 45.94 | 45.91 | 4.78 | 4.57 |
| V100 only | on | 44.34 | 44.51 | 6.25 | 6.23 |

MTP accepted 41/42 drafted tokens in every MTP cell. It increased GLM TG by about 31-42% for about a 3% PP cost. Fork PP is essentially unchanged on GLM.

Build the real semantic 10k slot from `seq11k.json` with:

```bash
./benches/v100-qwen38/glm52-10k-prepare-cache.sh
```

The default preparation placement is the final dual-GPU no-MTP `m768` fit. `ARGS_FILE`, `SERVER_BIN`, `MODEL`, `SEQ_JSON`, and `SLOT_DIR` can be overridden.

The generic GLM runner is:

```bash
./benches/v100-qwen38/glm52-10k-run-one.sh MODE BIN FIT_ARGS HW MTP UBATCH PORT
```

Examples corresponding to the final placements:

```bash
# dual, no MTP
./benches/v100-qwen38/glm52-10k-run-one.sh \
  dual-nomtp-upstream ../build-upstream-current/bin/llama-server \
  ../results/resumed-100k-benchmark-20260821/glm52-10k/fit-dual-ub4096/m768.args \
  dual 0 4096 19460

# dual, MTP
./benches/v100-qwen38/glm52-10k-run-one.sh \
  dual-mtp-upstream ../build-upstream-current/bin/llama-server \
  ../results/resumed-100k-benchmark-20260821/glm52-10k/fit-dual-mtp/m3072.args \
  dual 1 4096 19462

# V100 only, no MTP
./benches/v100-qwen38/glm52-10k-run-one.sh \
  v100-nomtp-upstream ../build-upstream-current/bin/llama-server \
  ../results/resumed-100k-benchmark-20260821/glm52-10k/fit-v100-ub4096/m1024.args \
  v100 0 4096 19464

# V100 only, MTP
./benches/v100-qwen38/glm52-10k-run-one.sh \
  v100-mtp-upstream ../build-upstream-current/bin/llama-server \
  ../results/resumed-100k-benchmark-20260821/glm52-10k/fit-v100-mtp/m3584.args \
  v100 1 4096 19466
```

`m3072` on V100-only MTP loaded but OOMed when the real MTP graph was allocated. `m3584` was the tightest tested working placement and left about 288 MiB free after graph setup.

## Fit commands used during placement tuning

The placements were generated with `llama-fit-params`, then validated with real requests because projected free VRAM does not include every transient CUDA allocation.

Examples:

```bash
# GLM dual GPU, 10k context
../build-upstream-current/bin/llama-fit-params \
  --model /models/GLM-5.2-UD-IQ2_XXS/UD-IQ2_XXS/GLM-5.2-UD-IQ2_XXS-00001-of-00006.gguf \
  -c 11120 -b 4096 -ub 4096 -ctk q8_0 -ctv q8_0 -sm layer -fitt 3072,3072 -lv 4

# GLM V100-only, 10k context
CUDA_VISIBLE_DEVICES="$V100_UUID" \
../build-upstream-current/bin/llama-fit-params \
  --model /models/GLM-5.2-UD-IQ2_XXS/UD-IQ2_XXS/GLM-5.2-UD-IQ2_XXS-00001-of-00006.gguf \
  -c 11120 -b 4096 -ub 4096 -ctk q8_0 -ctv q8_0 -sm layer -fitt 3584 -lv 4
```

The exact result JSON files from the development session are kept outside the source tree under `results/`.
