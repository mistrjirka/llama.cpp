## What appeared to crash

The bot run failed at 14:58:31 CET. Neither service exited during the incident. Before maintenance, llama.cpp still had its November 25 process, and the bot still had its November 25 process. Both had zero restarts. Kernel and service checks found no OOM kill, GPU Xid, assertion, or process crash explaining the report.

The final model request received HTTP 400. The server rejected an invalid Unicode surrogate in its JSON body at column 101643.

The source was a derived stored string. Its well-formed parent had an emoji encoded as two UTF-16 units at offsets 4799 and 4800. The derived value matched a slice starting at offset 4800, leaving only the second unit, U+DF3F. Its metadata identifies it as a derived run_code value. The creating script was no longer available after compaction, so its exact expression is not asserted.

The inspect_variable tool later exposed that malformed first unit with offset zero. The result was saved in conversation history. A restart alone would therefore reload the same bad history and could fail again.

The failed request was estimated at 48,383 tokens. That was below the bot's 95,000-token hard limit and the server's 110,080-token context. This failure was not a context-limit rejection.

## Why the run was slow

The run lasted 838.65 seconds, from about 14:44:33 to 14:58:32 CET.

| Component | Time |
|---|---:|
| Provider requests, 17 successful and one rejected | 797.89 s |
| Eight successful shell commands | 25.72 s |
| Other orchestration/tool overhead | 15.05 s |

There was no timeout retry loop. About 95% of the elapsed time was waiting on model requests.

### Existing image processed again

The first model request took 305.21 seconds. Its prompt processing took 245.76 seconds for 50,666 tokens.

A 155.9-second gap between progress updates aligns with an existing 1234 x 1194 JPEG and 1,443 image tokens. The image was already in the conversation. No new image was added at this point.

The server runs image encoding on the CPU. Source inspection found no cross-request cache for image embeddings. If checkpoint reuse starts before an image, it must be encoded again. CPU encoding is therefore the likely cause of the gap. The logs do not contain a direct image-encoder timer, so 155.9 seconds is the measured progress gap, not an exact encoder duration.

### Checkpoints clustered near the prompt end

Automatic compaction took 220.16 seconds. That request removed the image. Approximately 60,471-60,484 prefix tokens still matched, but only 14,981 were reused. It processed 58,007 tokens in 115.59 seconds before generation.

The earlier request had created checkpoints at 65,387, 65,507, and 65,643. The previous policy protected nearby checkpoints created during the same request. Those captures displaced checkpoints at 42,434 and 52,293.

The active list then held the base at 14,981 and two end points at 65,507 and 65,643. Both end points were after the compaction edit around 60,480, so the server fell back to the base and replayed about 45,500 unchanged tokens.

The November 25 fix was active. It handled nearby checkpoints from previous requests. This incident exposed the remaining same-request case.

## Changes

### BlackDogBot

Model-visible inspection text, previews, worker display output, and worker error text now replace isolated UTF-16 halves with the Unicode replacement character. Complete emoji remain intact. Stored raw values and UTF-16 pagination offsets are unchanged.

The outgoing request boundary also repairs malformed Unicode in decoded JSON values and keys before token accounting, hashing, and transmission. This handles malformed messages already stored in history. Ordinary request bytes and literal backslash escape text remain unchanged. Key collisions after repair fail locally rather than silently losing a value.

The fix does not retry the same invalid request indefinitely.

### llama.cpp

Under existing count or byte pressure, nearby checkpoints from the same request may now replace one another if they are within one actual runtime microbatch. The configured minimum spacing also caps this interval. The hub's effective microbatch is 256 tokens.

The recorded sequence now retains:

| Policy | Checkpoints |
|---|---|
| Before | 14,981 / 65,507 / 65,643 |
| Fixed regression | 14,981 / 52,293 / 65,643 |

Keeping 52,293 would have avoided 37,312 token evaluations in the recorded compaction request. This is a counterfactual calculation, not a measured replay of the user's original request.

The retained states remain independent complete checkpoints. Their serialization, model weights, sampling, and sharing format are unchanged. Eviction still stops once the incoming checkpoint fits.

There is a coverage tradeoff: a later edit inside a merged interval can fall back to an older checkpoint and replay more text. The extra replay is not necessarily limited to 256 tokens. Three checkpoints cannot cover every edit location.

## Current limits

CPU image encoding remains slow. The fix does not add an image-embedding cache or move the projector to VRAM.

At final verification, llama.cpp reported build b49-e28d562 and healthy status. Both services were active with zero automatic restarts and zero OOM events. The model had zero swap use. The bot cgroup had about 0.96 MiB in swap. GPU use was 11,149 MiB of 12,288 MiB.

The 4 GiB setting limits parked cache, not total process memory. No memory-budget increase was used for these fixes. Restarting llama.cpp cleared its previous cache, so the first resumed conversation may need a cold refill.
